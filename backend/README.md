# SoilEdge Field System — Backend

Python (FastAPI) backend for the smart-farming handoff spec.

**Frontend:** HTML + CSS + JS (separate)
**ESP32:** posts telemetry to `/api/telemetry`
**This service:** owns DB, JWT, Sentinel-2 health, scheduled jobs.

---

## Quick start

```bash
cd backend
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env
# edit SECRET_KEY and (optionally) Copernicus credentials

uvicorn app.main:app --reload --port 8000
```

Open the auto-generated docs at:

* Swagger UI → http://127.0.0.1:8000/docs
* ReDoc     → http://127.0.0.1:8000/redoc

`/api/health` reports DB connectivity and env.

## Auth model

* **Users** → `Authorization: Bearer <jwt>` (issued by `/api/auth/login`).
* **Devices** → `Authorization: Bearer <device_token>` *or* `X-Device-Token: …`.
  Token is generated by `/api/devices/register` and shown **once**. Stored as
  SHA-256 in the DB.
* Telemetry endpoint also enforces a per-device rate limit
  (`TELEMETRY_RATE_PER_MIN`, default 60/min).

## ESP32 telemetry payload

```http
POST /api/telemetry
Authorization: Bearer <device_token>
Content-Type: application/json

{
  "device_id": "field_1",
  "moisture": 28.5,
  "temperature": 26.1,
  "ph": 6.7,
  "ec": 1.4,
  "action": 1,
  "action_name": "Improve irrigation scheduling",
  "pump": true,
  "fertilizer": false,
  "timestamp": "2026-08-31T09:00:00Z"
}
```

The server:

1. authenticates the device token,
2. looks up the device's `field_id`,
3. inserts a row into `sensor_readings`,
4. inserts a row into `automation_events` (when the ESP32 sent a decision),
5. updates `devices.last_seen`.

## Sentinel / NDVI / NDWI

* Service: `app/services/sentinel.py`
  * `CopernicusClient` — real Sentinel Hub Process API call (NDVI+NDWI over
    the field polygon, with SCL-based cloud masking).
  * `MockSentinelClient` — used automatically when Copernicus credentials are
    missing. Returns plausible synthetic values so the pipeline can be
    exercised locally.
* Scheduler: `app/jobs/satellite_job.py` runs `refresh_all_fields()` every
  5 days. Each field is refreshed independently and gets a denormalised
  `health_status` / `health_reason` for fast dashboard rendering.
* Manual trigger: `POST /api/fields/{id}/satellite/refresh`.

## Health rules

`app/services/health_rules.py` combines:

* crop profile (NDVI expected band per growth stage)
* trend vs previous observation
* cross-check with latest soil moisture + EC

…and emits a verdict:

* `healthy` — all signals in range
* `moderate` — one or more minor deviations
* `high_stress` — multiple stress signals (sharp NDVI drop, EC ≥ 4, etc.)
* `unknown` — no data yet or scene too cloudy

The reason is a single human-readable string the dashboard can show
verbatim.

## Local end-to-end test

```bash
# 1. start the server
uvicorn app.main:app --reload

# 2. register a user
curl -X POST localhost:8000/api/auth/register \
  -H 'content-type: application/json' \
  -d '{"email":"farmer@example.com","password":"hunter22","full_name":"Demo"}'

# 3. log in
TOKEN=$(curl -s -X POST localhost:8000/api/auth/login-json \
  -H 'content-type: application/json' \
  -d '{"email":"farmer@example.com","password":"hunter22"}' \
  | python -c 'import json,sys;print(json.load(sys.stdin)["access_token"])')

# 4. create a field
curl -X POST localhost:8000/api/fields \
  -H "authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' \
  -d '{"name":"North plot","crop_type":"wheat","planting_date":"2026-08-01","lat":28.45,"lon":77.02}'

# 5. register a device (capture the plaintext token!)
curl -X POST localhost:8000/api/devices/register \
  -H "authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' \
  -d '{"device_id":"esp32-01","name":"ESP32 #1","field_id":1}'

# 6. post telemetry as the device
DEV_TOKEN=...   # from step 5
curl -X POST localhost:8000/api/telemetry \
  -H "authorization: Bearer $DEV_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"device_id":"esp32-01","moisture":24.0,"temperature":26.5,"ph":6.8,"ec":1.2,
       "action":0,"action_name":"Maintain regular soil monitoring",
       "pump":false,"fertilizer":false,
       "timestamp":"2026-08-31T10:00:00Z"}'

# 7. trigger a satellite refresh
curl -X POST localhost:8000/api/fields/1/satellite/refresh \
  -H "authorization: Bearer $TOKEN"

# 8. inspect the verdict
curl localhost:8000/api/fields/1/health -H "authorization: Bearer $TOKEN"
```

## Acceptance checks

1. ESP32 `POST /api/telemetry` → rows in `sensor_readings` and
   `automation_events`, `devices.last_seen` updated.
2. `POST /api/auth/login` returns a JWT → FE can call
   `/api/fields` and `/api/fields/{id}/readings`.
3. `/api/fields/{id}/health` returns `status` + `reason` + latest NDVI/NDWI.
4. `POST /api/fields/{id}/satellite/refresh` stores an observation
   (using `MockSentinelClient` if Copernicus creds are absent).

## Data + ML pipeline

The soil-AI decision tree and the empirical NDVI bands used by the
health scorer are **trained on real public datasets**, not hard-coded.
See `ml/README.md` for the full lineage.

| Component | Source | Samples |
|---|---|---|
| Decision tree (ESP32 firmware) | Smart-Agriculture (GitHub: ramonjsi) | 10,000 |
| Decision tree (CV / cross-check) | GCEK Irrigation-Dataset | 150 |
| Empirical NDVI bands | CY-Bench (WUR-AI/sample_data, wheat+maize ES+NL) | 137,000+ obs |

To re-train or update the bands:

```bash
cd backend
python3 ml/train_esp32_model.py     # → ml/artifacts/model_*
python3 ml/derive_ndvi_bands.py     # → ml/artifacts/ndvi_bands.json
bash     ml/smoke_test.sh           # end-to-end cURL smoke test
```

The trained C function (`ml/artifacts/model_tree.c`) is a drop-in for
the ESP32 firmware — copy it into the Arduino sketch folder, add the
`safe_classify()` wrapper from `ml/README.md` to handle sensor sanity
checks and the rare EC ≥ 8 class-4 (reclamation) case.

## Notes for the frontend agent

* All authenticated routes expect `Authorization: Bearer <jwt>` from
  `localStorage`. Save the token on login and redirect if missing.
* `/api/fields` (collection) already returns the dashboard overview
  shape — use it for the cards on `dashboard.html` directly.
* `/api/fields/{id}/readings/latest` for the "live soil" panel.
* `/api/fields/{id}/health` and `/api/fields/{id}/health/trend` for the
  Sentinel panel (status + reason + Chart.js trend).
* `/api/fields/{id}/events` for the automation log table.
* `/api/fields` and `/api/fields/{id}` are CRUD — use them on the
  Settings page.
